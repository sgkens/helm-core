# spritedump

Headless frame dump: renders HELM layouts with the real `Program.cs` renderer and writes each screen's sprite buffer as JSON, for the docs-site LCD preview (Epic 26 in the roadmap).

## Usage

Run from the repository root:

```bash
dotnet run --project tools/spritedump -- --out <dir> [--set bind=value ...] layouts/default
```

Output is one `<layout>.json` per input file, with one frame per screen and hardware profile (`TextPanel`, `WideLCD`, `CockpitSmall`, `CornerLCD`, `CockpitCorner`). Bind values are deterministic (hash of the bind name, 22 to 95) unless overridden with `--set`. Exit code is 1 if any layout fails to parse or render.

## How it works

`SpriteDump.csproj` compiles `HelmCore.cs` and `Program.cs` unchanged, together with a stand-in for the Space Engineers ingame API:

- `SeShim.cs`: hand-written types (`Vector2`, `Color`, `MySprite`, `IMyTextSurface`, `MyGridProgram`, enums).
- `SeShim.Blocks.cs`: generated by `gen.py`. Block members that `Program.cs` reads (`IMyBatteryBlock.CurrentStoredPower`, ...) are declared as `dynamic`, because the dump never reads blocks. Rerun `python3 gen.py` in this directory after `Program.cs` starts using new block members.
- `Dump.cs`: the harness. It injects values through the script's dynamic-value table and captures the sprites passed to `DrawFrame()`.

## Known limits

- Texture size is assumed to be a square of the larger surface side. It only affects the exported viewport offset.
- `MeasureStringInPixels` returns placeholder metrics (13 px per character per unit scale, 22 px line height). Layouts that depend on measured text width can differ from in-game output (Epic 26, TASK-26.5).
- The shim is not the real VRage code. Compile success here does not prove compile success in-game, but it catches missing types and wrong member names.
